# 核心可行性研究报告：轻量级前端体感交互架构

**编制日期**：2026年3月18日

**报告定级**：架构选型与高概念设计 (High-Concept & Architecture)

**核心目标**：构建零外设、防疲劳的儿童/家庭体感交互游戏 MVP

---

## 执行摘要 (Executive Summary)

本报告旨在解决"如何利用基础消费级摄像头为儿童构建高反馈体感游戏"的工程痛点。将传统游戏的高精度微操生硬移植到体感控制上是一个 UX 伪命题。

本报告确立了基于 **TensorFlow.js + Rapier2D + PixiJS 的纯前端（Client-Side Only）架构**。核心主张为：通过引入 2D 物理引擎的混沌反馈（多体碰撞）进行感官欺骗，从认知心理学层面掩盖视觉模型必然存在的追踪抖动（Jitter），从而在 60-90 秒的单局时间里，提供极高情绪价值且无生理疲劳的交互体验。

---

## 一、项目愿景与目标定位

本项目利用消费级摄像头（手机、平板或 PC），开发无需额外外设的轻量级体感交互游戏。目标受众以儿童（8 岁左右）及家庭互动场景为主。

传统游戏设计理念（精准跳跃、长时间移动）直接移植到体感控制上注定失败。核心开发哲学为：**降低操作精度要求，利用物理引擎的混沌反馈掩盖追踪算法的误差，并通过"短平快"的单局设计规避人体生理疲劳。**

### 1.1 设备场景与分级策略

体感追踪的精度与模型选择，**因游戏而异、因设备而异**：

| 设备 | 场景特征 | 适合的交互方式 |
|------|----------|----------------|
| **手机 (Phone)** | 屏幕小、距离近、需手持 | 头部动作（摇头、点头）、面部特征（张嘴、眨眼）、麦克风音量输入 |
| **平板 (Pad)** | 屏幕中等、可支架放置 | 上半身动态、手臂与头部联合协同、手势追踪 |
| **PC/Laptop** | 屏幕大、摄像头固定 | 完整手势追踪、双手协同 |

**算力基线**：以 2025 年中高端移动终端为起步体验标准，确保浏览器内 WebGL 推理和 60FPS 渲染流畅运行。

## 二、核心生理约束与二阶洞见

在确定技术架构前，必须正视人类生理结构的硬性约束：

### 2.1 颈椎疲劳与头部追踪的局限

人类颈椎不适合高频、大角度的定向微操。连续使用头部控制"上下左右"超过 5 分钟（95% 置信区间：$[3, 7]$ 分钟），极易引发肌肉劳损与视觉眩晕。因此，**头部追踪仅适合低频触发或异步辅助操作**（如张嘴释放全屏技能、歪头控制转向）。

### 2.2 "大猩猩手臂综合征"（Gorilla Arm Syndrome）

手势交互中，手臂长时间悬空会导致三角肌迅速酸痛。成年人无支撑悬空操作极限通常在 10-15 分钟（95% 置信区间：$[8, 18]$ 分钟），儿童耐受阈值更低。

### 2.3 二阶洞见（The Second-Order Insight）

手势追踪的坐标点必然存在高频抖动（Jitter）和自遮挡导致的信息丢失。试图通过前端算法完全消除这些问题（如引入复杂的卡尔曼滤波），不仅急剧推高算力成本，还会带来难以忍受的输入延迟。

**更优的解法是通过游戏设计进行"感官欺骗"**：引入 2D 物理引擎。当玩家的"粗糙"动作转化为物理世界中夸张的碰撞、倒塌和反弹时，大脑的注意力会被复杂的视觉奇观吸引，自然忽略操作初期的微小不精准，从而获得极大的情绪释放。

## 三、技术架构与最终选型

经过充分评估，确立**纯前端（Client-Side Only）架构**——部署成本最低、隐私安全性最高（视频流绝不上传）。

### 3.1 核心技术栈

| 层级 | 技术 | 选型理由 |
|------|------|----------|
| **视觉感知** | `@tensorflow-models/hand-pose-detection` (runtime: tfjs) | 跨平台一致性最佳。WebGL 后端在 Android/iOS/桌面均可用，无需分平台适配。包体比 MediaPipe 小约 1MB。 |
| **物理引擎** | `@dimforge/rapier2d-compat` | Rust 编写、WASM 编译，性能约为 Matter.js 的 2.5 倍以上。活跃维护，TypeScript 支持良好。gzip 后约 300KB。`-compat` 版本无需 top-level await，兼容性更好。 |
| **渲染层** | `PixiJS v8` | WebGL 为主力渲染器，实验性支持 WebGPU。全新 ParticleContainer 性能达 v7 的 3 倍以上。Sprite 管理、滤镜、混合模式等能力支撑"可爱精美"的画风目标。 |
| **音效** | `Howler.js` | 仅 7KB (gzip)。内置 Audio Sprite 支持，基于 Web Audio API，低延迟。游戏工作室出品，专为游戏音效设计。 |
| **UI 框架** | React + Vite SPA | 纯客户端应用，无需 SSR。Vite 提供极快的 HMR 和构建速度。 |
| **UI 状态** | Zustand | 极轻量（< 1KB），API 简洁。仅管理菜单/分数等 UI 状态，游戏逻辑不经过 React 渲染周期。 |

#### 为什么放弃 MediaPipe？

经实机测试，MediaPipe Hand Landmarker 在 Android Chrome 上的 GPU delegate 实际回退到 CPU（XNNPACK），仅能达到 7-8 FPS，完全无法满足游戏需求。TensorFlow.js 的 WebGL 后端在同等设备上表现稳定，且在 iPhone/iPad 上反而比 MediaPipe runtime 更快。为避免维护两套引擎的复杂度，统一选用 TensorFlow.js。

#### 为什么选 Rapier2D 而非 Matter.js？

Matter.js 近年更新极少，社区虽大但核心已趋于停滞。Rapier2D 基于 Rust/WASM，在多刚体碰撞场景（恰好是物理沙盒的核心需求）中性能优势显著，且持续活跃迭代。

### 3.2 数据流管道 (Data Pipeline)

```
摄像头 (WebRTC) → TF.js 手势推理 → 平滑滤波 → 状态机 → 视口映射 → Rapier2D 物理 → PixiJS 渲染
                                                                                    ↓
                                                                              Howler.js 音效
```

各阶段详解：

1. **WebRTC 获取本地摄像头视频流**（需 HTTPS 或 Localhost）。若用户拒绝授权，直接提示"需要摄像头才能游戏"，不做降级。
2. **TF.js 按帧提取手势关键点坐标** $(x_i, y_i, z_i)$，$i = 0 \ldots 20$（21 个手部关键点）。
3. **平滑滤波层**：采用指数移动平均（EMA）消除原始数据抖动：

$$S_t = \alpha \cdot X_t + (1 - \alpha) \cdot S_{t-1}$$

建议平滑系数 $\alpha \in [0.3, 0.5]$，在平滑度与响应延迟之间取平衡。$\alpha$ 越大响应越快但越抖，越小越平滑但越迟钝。

4. **状态机引擎**：基于几何距离计算，实时判断"捏合（Pinch）"、"张开"、"滑动"等离散事件。
5. **视口映射层（Viewport Projection）**：将归一化坐标 $(0 \sim 1, 0 \sim 1)$ 动态映射到设备物理分辨率。设定"有效活动捕捉区"，避免手部超出摄像头视场角。
6. **Rapier2D** 接收离散事件与连续坐标，更新物理世界状态。
7. **PixiJS** 渲染当前帧画面以及 UI 动态游标。
8. **Howler.js** 根据物理事件（碰撞、抓取、释放）触发对应音效。

### 3.3 视觉映射与 UI 启示性 (UI Affordance)

在无实体交互（Air-Gesture）场景中，不渲染写实的"肢体倒影"（开发成本高、易产生恐怖谷效应）。

**核心反馈体系：动态游标（Dynamic Reticle/Cursor）**

| 状态 | 视觉表现 | 音效 |
|------|----------|------|
| **常态（放松）** | 追踪坐标处渲染柔和的半透明虚线圆环 | 无 |
| **悬停（接近目标）** | 圆环轻微脉动，颜色渐变 | 轻微的"嗡"声反馈 |
| **触发（Pinch）** | 游标收缩、中心高亮，粒子拖尾（Trail） | 清脆的"咔"声 |
| **释放** | 游标弹性恢复，短暂扩散波纹 | 轻柔的"嘭"声 |

这能以极低的性能开销，在玩家大脑中补足触觉缺失产生的"本体感觉失调"，迅速建立精准的"手眼映射坐标系"。

### 3.4 音效反馈系统

音效是体感游戏情绪价值的核心组成部分，尤其对儿童用户。

**技术方案：Howler.js + Audio Sprite**

```javascript
// Audio Sprite 示例：将多个短音效合并到单个文件，减少 HTTP 请求
const sfx = new Howl({
  src: ['sfx-sprite.webm', 'sfx-sprite.mp3'],
  sprite: {
    grab:    [0, 200],    // 抓取
    release: [300, 300],  // 释放
    crash:   [700, 800],  // 碰撞/倒塌
    pop:     [1600, 150], // 气球爆破
    combo:   [1850, 500], // 连击奖励
    engine:  [2500, 2000, true] // 摩托引擎循环（loop）
  }
});
```

**设计原则**：
- **即时性**：音效延迟必须 < 50ms，使用 Web Audio API 模式（Howler.js 默认）。
- **Audio Sprite**：将所有短音效打包成单个文件，避免多文件加载延迟。提供 `.webm` (首选) 和 `.mp3` (兼容) 双格式。
- **音量层次**：碰撞/爆破等核心反馈音量最高，UI 交互音次之，环境音最低。
- **移动端注意**：Android 上 Audio Sprite 可能有 1-2 秒起始偏移问题，需通过用户首次交互触发 `Howler.ctx.resume()` 解锁 AudioContext。

### 3.5 游戏循环与状态管理

**原则：游戏逻辑脱离 React 渲染周期。** React 仅负责 UI 层（菜单、分数、设置面板），游戏主循环独立于 React 之外运行。

#### 主循环结构（固定时间步长）

```
const PHYSICS_STEP = 1 / 60; // 固定 60Hz 物理步进
let accumulator = 0;
let lastTime = 0;

function gameLoop(currentTime) {
  const deltaTime = (currentTime - lastTime) / 1000;
  lastTime = currentTime;
  accumulator += deltaTime;

  // 1. 读取手势追踪结果（来自 Web Worker 或主线程）
  updateHandTracking();

  // 2. 固定步长物理模拟（确保物理行为一致性）
  while (accumulator >= PHYSICS_STEP) {
    rapierWorld.step();
    accumulator -= PHYSICS_STEP;
  }

  // 3. 渲染（PixiJS 按实际帧率绘制）
  renderScene(accumulator / PHYSICS_STEP); // 插值系数用于平滑渲染

  // 4. 音效触发（基于物理碰撞事件）
  processAudioEvents();

  requestAnimationFrame(gameLoop);
}
```

#### 游戏状态机

采用简单的枚举状态机，不引入额外状态管理库：

```
[Idle] → 开始 → [Countdown] → 倒计时结束 → [Playing] → 时间到/条件达成 → [Result]
                                                ↑  ↓
                                            恢复  暂停
                                                ↑  ↓
                                              [Paused]
```

- **游戏内状态**（物理世界、分数、计时器）：纯 JS 对象，主循环直接读写，不经过 React。
- **UI 状态**（菜单显示、设置项、最终分数展示）：Zustand store，React 组件订阅。
- **桥接**：游戏结束时，主循环将最终分数写入 Zustand store，触发 React 渲染结算界面。

### 3.6 工程结构：Monorepo 多游戏矩阵架构

采用 **pnpm workspace + Vite** 的 Monorepo 结构：

```
motion-games/
├── packages/
│   └── motion-engine/        # 纯底层算法包
│       ├── src/
│       │   ├── tracking/     # TF.js 手势追踪封装、EMA 滤波
│       │   ├── physics/      # Rapier2D 物理世界管理
│       │   ├── audio/        # Howler.js 音效管理
│       │   ├── input/        # 状态机（捏合/释放/滑动检测）
│       │   └── hooks/        # React Hooks（useHandTracking, useGameLoop 等）
│       └── package.json
├── apps/
│   ├── hub/                  # 游戏大厅（React + Vite SPA）

```

- `packages/motion-engine`：封装 WebRTC 摄像头流、TF.js 实例生命周期、滤波降噪与状态机。向业务层只暴露干净的 React Hooks 或事件订阅接口。
- `apps/hub`：游戏大厅主体（React + Vite SPA），处理通用菜单入口和全局设定。
- `apps/game-*`：各独立小游戏。相互代码绝对隔离，各自专注于 PixiJS 渲染表现层的定制。

## 四、核心工程算法：捏合检测 (Pinch Detection)

所有手势交互的基础依赖于准确且鲁棒的"捏合"识别。基于特征点的空间几何计算，而非高延迟的图像分类。

### 4.1 距离计算

提取拇指指尖（Landmark 4）与食指指尖（Landmark 8）的坐标，计算欧几里得距离 $d$：

$$d = \sqrt{(x_4 - x_8)^2 + (y_4 - y_8)^2}$$

> 注：此处使用 2D 距离即可。z 轴（深度）数据噪声较大，引入反而降低鲁棒性。

### 4.2 死区与迟滞（Hysteresis）策略

为防止手指在临界距离微小抖动时引发高频误触发，在状态机中设置双阈值（施密特触发器原理）：

- 当 $d < T_{\text{grab}}$ 时，触发 `onGrab`（抓取状态激活）
- 当 $d > T_{\text{release}}$ 且处于抓取状态时，触发 `onRelease`（释放状态激活）
- **强制要求**：$T_{\text{release}} > T_{\text{grab}}$，差值即为"死区"

建议初始值：$T_{\text{grab}} \approx 0.04$（归一化坐标），$T_{\text{release}} \approx 0.07$。实际值需根据测试调优。

## 五、核心应用案例分析

基于"防疲劳、高反馈"设计理念，以下案例为首选落地项目：

### 案例 1：魔法物理沙盒 (Magic Physics Sandbox)

**核心机制**：屏幕中央生成由各类几何体、炸药桶构成的积木塔。玩家用"捏合"手势隔空抓取屏幕边缘的重型铁球，挥动手臂并松开手指，将铁球砸向积木塔。

**技术映射**：
- **Pinch (捏合)** → 触发抓取，将铁球的物理位置绑定至指尖坐标（Rapier2D Kinematic Body）
- **Move (挥动)** → 记录最近 $N$ 帧（$N \approx 5 \sim 8$）的坐标轨迹，计算瞬时速度向量
- **Release (松开)** → 解除绑定，将瞬时速度向量赋予铁球，交由 Rapier2D 进行抛物线与碰撞运算
- **碰撞音效** → Rapier2D 碰撞事件触发 Howler.js 播放对应音效（不同材质不同音色）

**二阶洞见**：儿童天生对"破坏结构"具有强烈心理诉求。积木倒塌的物理连锁反应配合丰富的碰撞音效，提供极其丰富的视听奖励，将注意力从"控制精准度"转移到"破坏的爽快感"上。

### 案例 2：气球捏捏乐 (Balloon Popper)

**核心机制**：屏幕底部以不同速度向上飘起彩色气球与"炸弹"气球。玩家需在气球逃逸前，用食指和拇指在对应位置精准"捏爆"彩色气球，同时避开炸弹。

**技术映射**：
- **Pinch** → 提取捏合瞬间的中心点 $P_c = \left(\frac{x_4 + x_8}{2},\ \frac{y_4 + y_8}{2}\right)$
- **碰撞检测** → 判断 $P_c$ 是否在气球包围圈内：$|P_c - C_{\text{balloon}}| < R_{\text{balloon}}$
- **爆破音效** → 捏中时 Howler.js 播放"啵"声 + PixiJS 粒子爆散特效

**二阶洞见**：极致简化但高效的"手眼协调"训练。单局游戏 60-90 秒，从根本上杜绝大猩猩手臂综合征。核心逻辑仅涉及 2D 圆形碰撞检测，是最适合验证整套数据管道的 MVP。

### 案例 3：咆哮摩托 (Roaring Motorbike)

**核心机制**：玩家扮演摩托车手（第三人称尾随视角），通过歪头控制左右转向，用嘴巴发出声音的音量控制加速/减速。

**技术映射**：
- **Head Tilt (头部侧倾)** → 提取面部关键点（双眼连线斜率），映射为平滑转向角。使用 TF.js 的 face-landmarks-detection 模型（比手部追踪轻量得多，移动端完全流畅）。
- **Audio Volume (麦克风)** → Web Audio API 的 `AnalyserNode`，解析实时音量作为引擎推力。音量越大，加速越快。
- **引擎音效** → Howler.js 循环播放引擎声，根据当前速度动态调节 `rate`（音调）和 `volume`。

**二阶洞见**：融合视觉（头部）与听觉（麦克风）的多维联动体验。让玩家用嘴巴"轰马达"极具"出丑效应"（Pratfall Effect），在家庭聚会中制造海量笑料。不需要手部追踪，**对移动端最友好**，适合作为手机端的主打游戏。

## 六、远景规划：多机协作与大屏架构 (Phase 2)

"手机做 Sensor，电视做 Display" 是极佳的技术拓展方向，但带来了设备配对、信令互通和 P2P 数据同步等网络复杂性。

此需求置于**二期研发（Phase 2）**。架构演进方向：**分离分布式运算**——手机端进行手势/面部追踪推理，通过 WebRTC Data Channel 将动作结果以微小体积发送给大屏设备，大屏仅负责画面渲染。
